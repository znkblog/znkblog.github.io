# 바이브코딩: 상권과 매출의 상관관계 분석

어느날 회사의 경영진이 궁금해했다. "상권일수록 매출이 잘 나오는 게 당연한 건가? 앞으로는 상권 중심으로 마케팅 자원을 집중적으로 쏟아야 하나?"

가만히 생각해보면 그럴 것 같다. "그렇겠지요?"라고 대답했더니 다음 질문이 이어진다. "어떤 상권일 때? 어느 정도로?" 보다 상세하고 깊은 질문이 이어지니 대답이 막히게 된다.

결국에는 상권과 회사 매출의 상관관계를 제대로 분석해보기로 하였다.

## 상권의 정의와 측정

분석을 시작하기 전에 먼저 생각해야 할 것이 있다. 상권이란 무엇인가? 측정은 어떻게 할 것인가?이다. 누구나 공감할 수 있는 **명확한 정의와 측정방법**을 사전에 정해야 했다.

정의부터 해보자. 보통 상권이 형성되어 있다고 말할 정도면, 유동인구가 많거나, 높은 빌딩이 많거나, 음식점/편의점같은 근린생활시설이 많거나, 의료나 공공서비스가 집중되는 지역이거나, 역전이나 랜드마크 주변이 되기도 하는 등 다양한 정의를 내릴 수 있다. 결국 상권을 분석하려는 이유를 가장 잘 설명할 수 있는 정의가 필요했기에 회사 매출과 가장 연관성이 높은 음식점으로 상권을 바라보기로 하였다.

다음으로는 어떻게 측정할 것이냐이다. 단순히 상권이 형성되어 있다/있지 않다로 말은 할 수 있겠지만, yes or no로는 분석을 위한 충분한 정량지표가 되지 못했다. 그래서 상권을 크기로 표시하기로 했다. 상권 크기의 정도는 음식점들이 얼마나 모여있는지 즉 밀집도로 보기로 했다. 이렇게 해야 측정에 객관성도 담보될 것 같았다.

종합하면 **상권을 나타내는 대표사물인 음식점이 단위면적 당 몇 개가 밀집되어 있느냐로 상권의 크기를 측정**하기로 하였다.

## 분석 방법

행정안전부에서 **전국 음식점의 인허가정보**를 정기적으로 제공한다.

[공공데이터포털](https://www.data.go.kr/data/15045016/fileData.do) 링크를 들어가서, `바로가기`를 클릭 후, 새로 열리는 화면에서 `전국 파일 다운로드`를 클릭하면 `식품_일반음식점.csv` 파일을 다운받을 수 있다. 약 680MB 정도로 제법 용량도 된다.

음식점들 인허가 사항 목록이 들어있는데 음식점별 좌표도 구할 수 있다. 각 지역을 1km² 격자 단위로 나눈 뒤, 음식점들의 좌표가 어느 격자에 해당하는가를 전체 추적하면, 격자마다 음식점 수를 구할 수 있다. 음식점 수가 많을수록 밀집도가 높을 것이고, 밀집도가 높은 격자는 상권의 크기가 큰 지역을 나타내게 된다.

여기에 회사 매출 정보를 좌표별로 가지고 와서, 그 매출도 어느 격자에 해당하는지 매칭을 해보면, `음식점 밀집도 - 격자 - 매출 정보`와 같이 격자를 중심으로 음식점 밀집도와 회사의 매출이 연결이 된다. 이 결과를 가지고 상관분석을 하기로 했다.

## 작업 방법

[copilot cli](https://github.com/features/copilot/cli?locale=ko-kr) 무료버전 사용하여 바이브코딩으로 아래와 같은 4개의 작업을 진행하기로 했다.

> - 공공데이터포털에서 받은 csv 파일 인코딩 변환
> - 음식점을 좌표별로 격자에 집계
> - 매출 좌표를 격자에 매칭
> - 상관관계 분석하여 pptx 출력

아래부터는 ai가 스스로 작성한 AGENTS.md 파일의 주요 내용으로 설명을 해본다.

## 공통 작업 원칙

```markdown
- 런타임은 Python 3.10 이상, 프로젝트·가상환경·의존성 관리는 `uv`를 사용합니다. 의존성 선언은 `pyproject.toml`, 잠금은 `uv.lock`, 설치·동기화는 `uv sync`, 스크립트 실행은 `uv run .\<스크립트>.py`로 합니다.
- 스크립트에서 CSV 입출력과 CLI에는 Python 표준 라이브러리(`csv`, `argparse`, `pathlib`, `tempfile`)를 우선 사용합니다. 외부 라이브러리는 `pyproject.toml`에 선언하고 `uv.lock`을 갱신합니다.
- 스크립트는 실행 순서에 맞춰 번호를 붙입니다. 인코딩 변환은 `01_convert_to_utf8.py`, 격자 집계는 `02_analyze_restaurant-grids.py`, 매출 격자 매칭은 `03_attach_sales_to_grids.py`입니다.
- 원본 파일 `식품_일반음식점.csv`는 약 680MB이므로 수정하지 마세요. 대용량 CSV는 전체를 메모리에 올리지 말고 스트리밍 또는 청크 단위로 처리하세요.
- 결과 CSV는 별도 요청이 없는 한 Excel에서 한글이 올바르게 보이도록 UTF-8-SIG(BOM 포함)과 `newline=""`로 기록합니다.
```

본인이 좋아하는 python 과 uv 패키지 관리툴을 사용할 것을 주문했다. 대략적인 분석 방법을 알려주었고 필요한 외부라이브러리 및 환경설정은 ai에게 맡겼다.

위에 언급한 4개의 작업 중 위 3개는 스크립트를 각각 작성하도록 했다. 그리고 제일 마지막 작업인 pptx 외에는 모든 결과가 csv인데, 엑셀에서도 문제없이 열리도록 utf-8-sig 인코딩을 사용하도록 했다.

csv가 클수록 한 번에 메모리에 올리면 부담이 될 수 있으니, 큰 용량의 파일은 부분부분 배치로 읽어가면서 처리하도록 했다.

## csv 인코딩 변환

```markdown
- `--source-encoding`이 주어지면 그 인코딩을 사용합니다. 지정하지 않으면 먼저 파일 시작의 UTF-32/UTF-8/UTF-16 BOM을 확인하고, BOM이 없을 때 `charset-normalizer`로 파일 앞 2MiB만 검사해 원본 인코딩을 추정합니다. 자동 감지는 표본 기반 추정이므로 애매하거나 감지할 수 없는 파일은 인코딩을 직접 지정하세요.
- 입력은 1MiB씩 읽고, 출력은 UTF-8 바이트와 파일 시작의 BOM으로 기록합니다. CSV 필드나 행을 파싱·재직렬화하지 않아 내용 및 줄바꿈 바이트는 유지하며, 문자 인코딩만 변환합니다.
```

현대의 pc 환경에서 주 인코딩은 utf-8이지만, 과거 레거시 호환성 때문인지 여전히 공공데이터 등은 EUC-KR이나 CP949 등 다른 인코딩을 사용하는 경우가 많고, 공공데이터에서 받은 csv 파일 또한 그렇다.

utf-8이 아닌 경우 인코딩 호환이 안되어 한글처리에 문제가 생길 수 있으므로, 공공데이터포털에서 받은 파일을 utf-8-sig 인코딩으로 재저장을 하도록 했다. (utf-8-sig 인코딩을 사용하면 csv 파일이 엑셀에서도 문제없이 잘 열린다.)

## 음식점 좌표 격자 집계

```markdown
- `영업상태명`을 앞뒤 공백 제거 후 `영업/정상`과 정확히 비교합니다. 일치하는 행만 처리하며 `좌표정보(X)`, `좌표정보(Y)`의 앞뒤 공백을 제거해 숫자로 변환합니다. 비어 있거나 숫자가 아니거나 유한수가 아닌 좌표는 제외하고 건수를 알립니다. 매출 격자 스크립트와 달리 좌표의 EPSG 범위 검증은 하지 않습니다.
- 좌표값은 이미 보정계수 미적용 Bessel 중부원점TM(EPSG:5174)이라고 가정하고 변환하지 않습니다. 입력을 한 번 스트리밍해 유효 좌표 범위를 구하고, 두 번째 순회로 격자별 개수를 집계합니다.
- 격자 크기는 1000m입니다. 격자 시작 X는 `floor(min_x / 1000) * 1000`, 시작 상단 Y는 `ceil(max_y / 1000) * 1000`입니다. X 셀은 `[왼쪽 X, 오른쪽 X)`, Y 셀은 `(아래쪽 Y, 위쪽 Y]`로 배정합니다. 따라서 경계 좌표는 각 방향에서 정확히 한 셀에 포함됩니다.
- 전체 좌표 범위를 덮는 직사각형 격자 전체를 출력하며 음식점이 없는 셀도 개수 0으로 포함합니다. ID는 위에서 아래 행 우선, 각 행에서 왼쪽에서 오른쪽 순으로 `G000001`부터 부여합니다. 열은 `격자ID`, `격자좌상단좌표정보(X)`, `격자좌하단좌표정보(Y)`, `음식점카운팅` 순서입니다.
```

인코딩 변환 후의 공공데이터포털 csv 파일을 열어서, 폐업이 아닌 `영업/정상` 음식점만 추리도록 했다. (약 65만여 개가 나왔다.) 음식점들의 X, Y 좌표들을 모두 포함하는 큰 범위를 파악한 뒤, 각 면적이 1km²가 되는 격자로 나누도록 했다.

참고로 공공데이터포털 사이트에 보면 좌표계가 EPSG:5174라고 나온다. 이 좌표계는 1단위가 정확히 1m에 대응하도록 되어있다. 시작 격자의 위치를 잡아주고, 각 격자는 ~이상 ~미만으로 설정해달라고 했다. (위 AGENTS.md 파일의 3번째 대시 부분이 이에 해당한다.)

격자별로 음식점수를 집계해서 다른 csv로 저장하도록 하였다.

## 매출 좌표 격자 매칭

```markdown
- `pyproj.Transformer.from_crs("EPSG:4326", "EPSG:5174", always_xy=True)`로 격자 좌표계에 변환합니다. 격자 산출과 동일하게 X는 왼쪽 포함·오른쪽 미포함, Y는 아래쪽 미포함·위쪽 포함 경계를 사용합니다. 격자에 매칭되지 않는 행은 조용히 결과에서 제외하며 요약에 격자 범위 밖 건수를 표시합니다.
- 매출액은 숫자로 변환하거나 격자별 합산하지 않습니다. 앞뒤 공백을 제거한 원래 문자열을 각 매출 행마다 출력하고, 해당 격자의 `격자ID`, `음식점카운팅`을 붙입니다. 출력 열은 `매출액`, `격자ID`, `음식점카운팅` 순서입니다.
```

회사의 좌표별 매출 데이터를 csv로 가져왔다. (여기서는 실제 매출이 아닌 fake 매출 정보를 임의로 생성했다.)

회사의 좌표는 EPSG:4326(WGS84라고도 함)으로 이는 흔히 말하는 위도/경도 좌표계이다. 좌표계가 다르므로 이를 EPSG:5174에 맞추도록 주문했다. 그리고 매출액별로 격자ID와 음식점수(격자 면적이 1km² 이므로, 격자 안의 음식점 수는 곧 음식점 밀집도가 됨)를 다시 csv에 담도록 했다.
